## #49 Mac 调度 tick 停摆：栈一倒，全 rc=7，样本不再更新

- **现象**：准确率样本停在 320 不动；`GET /health` 的 `jobRuns.lastRunAt` 冻结在 2026-10-15。
- **根因**：外部调度靠 launchd 每 60s `curl 127.0.0.1:8080/api/admin/scheduled` 触发轮次。一旦 Docker 栈（nginx:8080）没在监听，tick 全部 `curl rc=7`（connection refused），所有交易日轮次静默跳过——而 `scheduler-tick.sh` 成功空跑不写日志、仅失败才写，故日志尾停在宕机期，容易被误判成"调度器没装"。
- **定位**：`docker compose ps` 看容器是否 Up；`curl -sv 127.0.0.1:8080/health` 看 8080 是否通；`bash scripts/install-mac-scheduler.sh --status` 看 launchd 是否加载、日志尾。
- **教训**：tick 能否跑**完全取决于栈是否活着**。栈不是 tick 的一部分，必须独立保活——这是 #52 加固要解决的。
- **关联**：`scripts/scheduler-tick.sh`、`scripts/install-mac-scheduler.sh`、`backend/app/market_schedule.py`。

## #50 Mac 主源 A 域名被网络层 SNI 拦截（Tushare ConnectError，非额度）

- **现象**：Mac 上 evaluate 满屏 `请求失败（ConnectError）：`，Windows 正常。
- **根因**：**不是** Tushare 额度耗尽（额度耗尽是 `code=42901` 业务错、HTTP 200、自动回落 B 套）。实测是 Mac 网络对主源 A 域名 `quantdata888.duckdns.org` 的 TLS 握手做 **SNI 层拦截**：裸 TLS 走该域名 `SSLEOFError`，直连其 IP / 走 B 域名 `pcd.mobcvb.cn` 均正常。
- **定位（四重对照）**：① A 裸 TLS → 失败；② 通用站点 baidu/github → 200；③ 直连 A 的 IP `38.76.160.225` 带 Host 头 → 200；④ Mac 主机走 A 域名 → `ConnectionResetError [54]`。结论：域名 SNI 被掐。
- **修复**：Mac `.env` 置空 `TUSHARE_TOKEN=`（让 `tushare_client._call` 跳过被拦的主源 A、直接走 B 套）；改完**必须 `docker compose up -d` 重启 backend** 才生效。B 套用独立 `tushare_fallback_api_key` 鉴权，不受影响。
- **关联**：`backend/app/tushare_client.py`（`_call` / `_post_primary` / `_get_fallback`）。

## #51 盘中评估"当日到期"预测全 missing 是时序假象，不是 bug

- **现象**：`evaluate_due_predictions()` 返回 `{'status':'completed','evaluated':0,'missing':200,'expired':0,'pendingRemaining':800}`，due 一直卡 200。
- **根因**：`due` = `status==pending 且 maturityTradeDate<=今天`。这 200 条 maturity **全是今天 2026-10-20**；盘中（15:00 上海闭市前）B 中继还没有当日收盘，故 `_fetch_close` 返 `None` → 进 `missing` 分支且 `overdue<=_EXPIRY_DAYS(20)` → 留 pending（`prediction_pipeline.py:425-438`）。对 `301230.SZ` maturity `20261020` 直探 B 返 `rows:[]`（**空、无报错**）= B 中继正常，只是此刻没数据。
- **定位**：`due by maturity` 分布（预期全今天）；对 top due code 直探 `_call('daily', ...)` 看是空（时序）还是报错（B 挂）。
- **教训**：`evaluated` 仍 320 是因为没有"过去到期且仍可评"的待评预测（过去的都在 tick 死前评完了），**不是停滞**。闭市后 B 落当日 close，当晚 17:40 / 22:00 的 `prediction-evaluate` 轮次自动评级，无需手动补跑（除非等不及，可闭市后手动跑一次）。
- **关联**：`backend/app/prediction_pipeline.py`（`evaluate_due_predictions` / `_fetch_close` / `_EXPIRY_DAYS=20`）。

## #52 Mac 隔夜轮次怕睡眠 + 重启栈不自起 → harden 脚本三件套根治

- **现象**：即使 tick/栈当前正常，仍可能重演 #49（尤其 Mac 空闲休眠错过 07:20 / 22:00 轮次，或重启后栈没起、tick 空打 rc=7）。
- **根因**：① launchd **LaunchAgent 不唤醒睡眠的 Mac** → 隔夜轮次被静默跳过且不补跑（`apply_daily_catch_up` 是 no-op）；② `scripts/deploy.sh` **不装调度器**（手动步骤），重部署不保活；③ 重启后无 boot 级机制拉起 `docker compose up -d`。
- **修复**：新增 `scripts/harden-mac-scheduler.sh`（一键装三件套，已提交 `origin/main` commit `dc3d7d4`）：
  1. **tick 常驻**：调既有 `install-mac-scheduler.sh`，用户级 LaunchAgent，每 60s POST `/api/admin/scheduled`；
  2. **栈保活** `com.stock-intelligence.stack`：每 5 分钟跑 `scripts/ensure-stack-up.sh`（幂等——`docker` 没起先拉 Docker Desktop，再 `docker compose up -d`），栈挂**最多 5 分钟自愈**，从根上消除"栈倒→tick 全 rc=7"；
  3. **防睡眠** `com.stock-intelligence.insomnia`：`caffeinate -dimsu` 常驻 + `pmset sleep 0`，保隔夜 07:20 / 22:00 轮次命中。
- **用法**：`bash scripts/harden-mac-scheduler.sh` 安装；`--status` 查看（三个 agent 应 Loaded、`pmset` 睡眠被 caffeinate 拦截、`docker compose ps` 两容器 Up）；`--uninstall` 卸载（如需恢复睡眠：`sudo pmset -a sleep 30`）。
- **验证（Mac 实测 2026-10-20）**：三 agent 均 Loaded，栈两容器 healthy，10:30 / 11:35 轮次成功触发，`JobRuns.lastRunAt` 持续推进。
- **关联**：`scripts/harden-mac-scheduler.sh`、`scripts/ensure-stack-up.sh`、`scripts/install-mac-scheduler.sh`、`scripts/scheduler-tick.sh`。
